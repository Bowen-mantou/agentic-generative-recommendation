## 1. 文档目的与决策摘要

本文件将最新确认的 TIGER 路线和后续阶段执行顺序固化为实施方案，作为
Phase 4--7 的开发依据。

### 1.1 已确认的核心决策

**Q1：采用 B→A（重解释）路线。**

这里的 B 不再表示直接使用外部预训练权重，而是：

-   复用外部 TIGER 项目的代码、模型结构和训练流程；
-   使用本项目自己的 All_Beauty 商品目录和用户交互数据；
-   使用本项目已有的 E5 商品向量作为商品表征输入；
-   在本项目数据上重新训练 RQ-VAE，生成本项目商品集合对应的 Semantic
    ID；
-   使用本项目用户行为序列训练自回归生成模型；
-   最终生成并解码本项目商品目录中的商品。

因此，本路线是**复用工程实现、使用自有数据重新训练核心模型**，而不是直接依赖外部模型权重进行商品推荐。

**训练策略：采用 A3，先 Pilot，再决定是否全量训练。**

-   Pilot 首先尝试 A1 配置；
-   如果 A1 暴露出明确的编码质量或生成效果问题，再开展 A2 对照；
-   只有 Pilot 达到预先约定的验收条件，才进入全量训练；
-   不允许用 Mock、随机 Semantic ID 或规则映射代替真实生成式召回。

**Q11：第一阶段不接入 MUSA。**

CPU 作为工程基线，但这不等于已经证明 CPU 一定能够承担所有 TIGER
训练任务。TIGER Pilot 必须先测量真实资源消耗，再决定可行的训练规模。

**Q12：Phase 0--6 的完整系统验收仍然要求真实 TIGER + E5 双路召回。**

若 TIGER
最终无法在项目预算内完成，必须提交偏差说明并由项目负责人重新批准；不得将
E5 单路系统描述为已完成双路召回验收。

## 2. Phase 4：TIGER 实施方案

### 2.1 Phase 4 的目标

Phase 4 的目标不是单纯训练一个
RQ-VAE，而是建立一条真实可运行的生成式召回链路：

1.  将本项目商品向量编码为 Semantic ID；
2.  将用户历史商品交互转换为 Semantic ID 序列；
3.  使用自回归模型学习用户序列中的下一商品预测；
4.  根据用户历史生成后续 Semantic ID；
5.  将生成结果解码并映射回本项目真实 `product_id`；
6.  输出 TIGER 候选商品列表，供 Candidate Fusion 使用。

RQ-VAE 重建效果好、Semantic ID 可以生成，均不能单独证明 TIGER
推荐有效。最终必须验证生成结果能否解码为有效商品，以及下一商品预测效果。

### 2.2 外部代码复用范围

外部 TIGER 项目仅作为实现参考和代码基础。正式使用前必须完成以下检查：

  检查项         要求
  -------------- ------------------------------------------------------------
  License        确认代码、配置、依赖和可能使用的第三方组件允许当前使用方式
  代码可运行性   能在当前环境安装依赖并运行最小示例
  模型结构       能定位 RQ-VAE、Semantic ID 编码/解码和自回归生成模块
  训练入口       能明确数据输入格式、训练命令、checkpoint 输出和恢复方式
  向量接口       能接收本项目 768 维 E5 商品向量，或能以明确适配层接入
  商品映射       能保存 Semantic ID 与本项目 `product_id` 的稳定映射
  序列接口       能接收本项目构造的用户历史序列
  推理接口       能生成 Semantic ID，并解码到商品目录中的真实商品

如果外部代码依赖特定数据集、商品 ID
或不可复用的预训练权重，需要先评估适配成本。不得仅因为仓库名称或论文名称相同，就认为实现与本项目兼容。

**复用代码不等于复用外部权重。** 本项目的 RQ-VAE
和自回归生成模型使用本项目数据重新训练。

### 2.3 数据准备

#### 商品侧数据

输入为当前 All_Beauty 商品目录及已有 E5 商品向量。

已知初始数据情况：

-   商品目录约 112,590 个商品；
-   E5 向量维度为 768；
-   当前 E5 checkpoint 为 `intfloat/e5-base-v2`；
-   商品内部主键统一使用 `product_id`；
-   保留 `product_id` 与 Amazon `parent_asin` / `asin` 的映射关系。

RQ-VAE 训练前必须检查：

-   向量文件与商品目录行数是否一致；
-   `product_id` 是否唯一；
-   是否存在缺失、NaN、Inf 或异常向量；
-   向量归一化方式是否与现有 E5 索引一致；
-   训练、验证和测试商品划分是否符合实验设计；
-   Semantic ID 解码结果是否始终能够映射回有效商品。

商品向量的生成方式、归一化和 checkpoint 版本必须写入
manifest，确保训练和推理使用同一套商品表征。

#### 用户交互数据

用户序列从 Amazon Reviews 2023 的 All_Beauty 交互记录构建。

建议保留以下字段：

``` python
{
    "user_id": "...",
    "product_id": "...",
    "event_timestamp": "...",
    "event_type": "review",
    "source": "amazon_reviews_2023",
    "is_simulated": False
}
```

说明：

-   Amazon Reviews 中的 review
    记录是可观测的评论/交互事件，不应直接称为购买记录；
-   不得将模拟点击、模拟喜欢或模拟购买混入真实训练序列；
-   同一用户的事件必须按时间排序；
-   必须处理重复事件、无效商品映射和时间戳异常；
-   训练、验证、测试必须遵循时间切分，避免未来行为泄漏。

需要在下载并解析 Reviews
后重新核验用户数、事件数和序列长度分布。当前"8,201 条长度至少为 3
的序列"应视为已有初步统计，不能替代对正式数据快照的重新统计。

### 2.4 Pilot 配置：A3

A3 是实验策略，不是第三种模型结构。Pilot 先执行 A1；A1
结果不足以支持全量训练时，再决定是否测试 A2。

#### A1：首轮 Pilot 配置

  参数                       配置
  ------------------ ------------
  RQ-VAE 码本数量               3
  每个码本大小                256
  组合编码空间           (256\^3)
  初步用户序列门槛       长度 ≥ 3
  已有初步序列统计       8,201 条
  商品向量输入维度            768
  商品目录规模         约 112,590

A1 作为首轮基线，主要用于验证 RQ-VAE 训练、Semantic ID
分配、用户序列转换和生成式召回的完整技术链路。

#### A2：必要时开展的对照配置

  参数                               配置
  ------------------ --------------------
  RQ-VAE 码本数量                       4
  每个码本大小                       1024
  组合编码空间                  (1024\^4)
  初步用户序列门槛               长度 ≥ 2
  可用序列数量         待下载和统计后确认
  商品向量输入维度                    768

A2 不自动优于
A1。更大的组合编码空间不代表更好的编码质量或推荐效果；更低的序列门槛也会改变训练样本构成。

**A1 与 A2 对照时必须控制变量。**

至少应区分两类实验：

1.  **码本配置对照：**
    尽可能固定相同用户、相同时间切分和相同训练样本，比较 3×256 与 4×1024
    的编码及生成效果。
2.  **序列门槛对照：** 单独比较长度 ≥3 与长度 ≥2
    对样本数量、序列长度分布和下一商品预测的影响。

不能同时改变码本配置和用户样本范围后，将结果差异全部归因于码本大小。

### 2.5 Pilot 执行步骤

#### Step 1：数据与代码审计

交付内容：

-   外部实现仓库地址、commit 或 release 版本；
-   License 检查记录；
-   依赖环境与运行说明；
-   All_Beauty 商品向量数据检查报告；
-   Reviews 数据下载与字段检查报告；
-   用户交互序列统计报告；
-   训练资源预估。

在这些信息明确前，不启动长时间全量训练。

#### Step 2：RQ-VAE 小规模训练

先使用 A1 配置完成小规模训练。

需要记录：

-   训练和验证重建误差；
-   各码本的使用频率；
-   Codebook Utilization；
-   Dead Code 数量和比例；
-   Semantic ID 分布；
-   Semantic ID 唯一性和商品映射覆盖率；
-   训练时间、峰值内存/显存和 checkpoint 大小。

RQ-VAE
的验收重点是编码稳定性、码本使用情况和商品可解码性，而不是只看训练
loss。

#### Step 3：自回归生成模型小规模训练

使用 RQ-VAE 生成的 Semantic ID，将用户历史交互转换为 Semantic ID 序列。

训练目标为基于历史序列预测后续商品的 Semantic ID。

需要记录：

-   训练样本数量和序列长度分布；
-   训练/验证/测试时间边界；
-   Next-item Recall@K；
-   NDCG@K；
-   MRR；
-   生成 Semantic ID 的合法率；
-   Semantic ID 解码成功率；
-   解码后的商品目录覆盖情况；
-   训练时间和推理延迟。

生成器结构、参数规模和训练超参数应在 Pilot
配置文件中显式记录。当前方案不预先锁定未经验证的生成器规模。

#### Step 4：Pilot 评审

Pilot 结束后，提交一份简短评审报告，至少回答：

1.  外部代码是否能稳定运行？
2.  RQ-VAE 是否能够为商品目录生成稳定 Semantic ID？
3.  码本是否出现严重塌缩或大量 Dead Codes？
4.  自回归模型是否学到可验证的下一商品预测能力？
5.  生成结果是否能够稳定解码为真实商品？
6.  当前设备和时间预算是否支持扩大训练？
7.  A1 是否足以进入全量训练？若否，A2 能解决什么具体问题？

根据报告决定： - A1 达标：继续 A1 全量训练； - A1 有明确编码问题：开展
A2 受控对照； - A1/A2
均不满足要求或资源超预算：提交偏差与替代方案，等待负责人批准。

### 2.6 Phase 4 验收标准

Phase 4 必须同时满足以下条件，才能标记为完成：

  验收维度   必须提供的证据
  ---------- -----------------------------------------------------
  真实编码   RQ-VAE 对本项目商品向量完成训练和编码
  商品映射   Semantic ID 能稳定映射回真实 `product_id`
  真实序列   自回归训练使用真实来源、按时间构建的用户交互序列
  真实生成   模型能根据用户历史生成 Semantic ID
  解码有效   生成结果能解码为商品目录中的有效商品
  离线效果   提供时间切分下的 Recall@K、NDCG@K、MRR
  资源记录   提供训练时长、推理延迟、峰值内存/显存和模型大小
  可复现性   保存数据快照、代码版本、配置、checkpoint 和运行命令

仅完成 RQ-VAE，或者仅能生成随机/规则 Semantic ID，均不算 Phase 4 完成。

## 3. Phase 5：Planner、Judgment 与 Adaptive Controller

Phase 5 可以先使用当前 E5 + FAISS 候选池完成端到端联调，不必等待 TIGER
训练结束。TIGER 完成后通过统一 Retrieval Interface 接入。

### 3.1 模块职责

  -----------------------------------------------------------------------------------------------------------------
  模块                    职责                                                       不负责的工作
  ----------------------- ---------------------------------------------------------- ------------------------------
  Planner / Replanner     解析当前需求、结合 Memory                                  不直接执行商品检索
                          生成结构化检索计划；根据失败原因重新规划                   

  E5 / TIGER Retrieval    按计划召回候选商品                                         不决定最终是否停止

  Python Constraint       执行价格、品类等确定性硬约束                               不使用 LLM 猜测缺失属性
  Evaluator                                                                          

  Qwen3-Reranker-0.6B     对候选商品进行相关性精排                                   不决定是否 Replan

  Judgment                判断商品对当前需求的语义适配性、偏好符合程度和证据充分性   不重复执行硬约束比较，不替代
                                                                                     Reranker

  Controller              综合候选数量、精排结果、Judgment、约束结果和预算决定       不自行生成检索计划
                          REPLAN 或 STOP                                             

  Recommendation          根据最终候选和证据生成推荐列表及理由                       不编造商品属性或缺失证据
  Generator                                                                          
  -----------------------------------------------------------------------------------------------------------------

### 3.2 Planner / Replanner

-   使用 DeepSeek API；
-   初始规划和重新规划共用模型与接口，通过不同 `mode` 区分；
-   输出遵循项目统一的 `RecommendationPlan` Schema；
-   Replanner
    输入包括原始需求、当前计划、已执行动作、候选/判断摘要和失败原因；
-   所有检索策略和预算均由结构化字段表达，不依赖自由文本解析。

### 3.3 Judgment：逐商品判断，批量 API 调用

Judgment 对每个候选商品产生独立判断结果，但工程上可以将多个商品放在一次
DeepSeek API 请求中批量处理。

例如，一次请求包含 10 个候选商品，要求模型返回 10 条彼此独立、可按
`product_id` 对齐的结构化判断。

建议输出概念：

``` json
{
  "items": [
    {
      "product_id": "product_001",
      "semantic_fit": "high",
      "preference_fit": "medium",
      "evidence_sufficiency": "sufficient",
      "reason": "商品信息与当前需求中的保湿诉求相符"
    }
  ]
}
```

要求：

-   每个输入商品必须有对应结果；
-   结果必须携带原始 `product_id`；
-   不能让模型新增输入中不存在的商品；
-   不能把缺失属性推断为已满足；
-   Python 产生的硬约束结果作为独立字段传入 Controller，不由 Judgment
    覆盖；
-   JSON 解析失败或结果缺项时，按失败策略处理并记录日志。

### 3.4 Controller

Controller 使用 LangGraph + Python 实现。

输入至少包括：

-   当前 `RecommendationPlan`；
-   当前候选商品及来源；
-   Python 硬约束结果；
-   Reranker 分数和排序；
-   Judgment 结果；
-   已执行的检索与重规划次数；
-   剩余 API 和检索预算。

核心动作：

-   `REPLAN`：当前候选数量、相关性、约束或证据不足，需要重新规划并再次召回；
-   `STOP`：当前候选已达到可接受输出条件，进入 Recommendation
    Generator。

所有路径必须受最大 Replan
次数和预算限制，避免无限循环。预算耗尽时必须走明确的降级或安全结束路径。

当前预算数值是初始配置，不代表已经通过验证集校准。阈值校准按照项目既定的"Amazon
时间切分数据 + 人工/模拟审核集"方案执行。

### 3.5 Phase 5 验收

-   Planner 能输出合法且符合统一 Schema 的计划；
-   Replanner 能根据失败原因产生结构化的新计划；
-   E5 候选池能够完成完整联调；
-   Python 硬约束正确处理 `pass`、`fail`、`unknown`；
-   Reranker 能返回可复现的排序分数；
-   Judgment 能逐商品返回结构化结果；
-   Controller 能正确走 REPLAN 和 STOP；
-   最大轮数、API 预算和检索预算能够阻止无限循环；
-   所有节点的输入、输出、错误和耗时均有轨迹记录。

## 4. Phase 6：Generator、Memory 与反馈闭环

### 4.1 Recommendation Generator

使用 DeepSeek API 生成最终推荐结果。

输入：

-   用户当前需求；
-   相关 User Memory；
-   最终候选商品；
-   Reranker 排序结果；
-   Judgment 结果；
-   商品可验证属性和约束结果。

输出：

-   Top-K 商品；
-   每个商品的推荐理由；
-   与用户需求的对应关系；
-   必要时明确说明信息缺失或无法确认的属性。

生成器必须遵循证据约束： - 只能推荐输入候选集合中的商品； -
商品价格、品牌、规格等属性必须来自商品目录或其他明确证据； -
不得补造缺失价格或产品功效； - 对未知属性使用谨慎表述； -
推荐理由应能追溯到需求、Memory 或商品证据。

### 4.2 Memory 部署

采用已确认方案：

-   Mem0：管理语义记忆；
-   独立 Qdrant：存储和检索向量记忆；
-   本地 Embedding：完成记忆向量化；
-   SQLite InteractionHistory：保存结构化、有时间顺序的用户行为事件；
-   LangGraph State：保存当前请求和会话上下文。

三类数据不能混用：

  ------------------------------------------------------------------------------
  数据类型                       存储位置                用途
  ------------------------------ ----------------------- -----------------------
  长期偏好、近期兴趣、明确反馈   Mem0 + Qdrant           Planner 和推荐个性化

  点击、评论等有时间顺序的事件   SQLite                  用户行为分析和 TIGER
                                 InteractionHistory      序列构建

  当前需求、当前轮上下文         LangGraph State         当前任务执行
  ------------------------------------------------------------------------------

### 4.3 反馈写入与模拟数据隔离

反馈事件至少包含：

``` python
{
    "user_id": "user_001",
    "product_id": "product_001",
    "event_type": "like",
    "event_timestamp": "...",
    "source": "simulated",
    "is_simulated": True
}
```

规则：

-   真实数据和模拟数据必须可区分；
-   模拟反馈可用于验证 Memory 更新和多轮交互；
-   模拟事件不得混入真实 TIGER 训练序列或真实行为评测；
-   只有经过定义的有效反馈才写入长期 Memory；
-   不得把单次模糊表达直接升级为长期稳定偏好；
-   支持按 `user_id` 隔离读取、更新和删除；
-   记录 Memory 更新前后变化，便于调试和审计。

### 4.4 Phase 6 验收

-   Generator 能根据最终候选输出 Top-K 和理由；
-   输出商品均来自候选集合；
-   商品事实有可追溯来源；
-   Mem0 和 Qdrant 能完成写入、检索、更新和删除；
-   多用户隔离测试通过；
-   模拟反馈不会污染真实行为数据；
-   Memory 更新能在后续请求中被正确检索；
-   系统能完成至少一条多轮购物对话闭环。

## 6. Phase 7：评测与消融实验

Phase 7 不只是展示系统能运行，还需要验证每个模块是否带来实际收益。

### 6.1 数据切分原则

-   使用 All_Beauty 真实来源交互记录；
-   按时间进行训练、验证、测试切分；
-   用户历史只能使用预测时点之前的事件；
-   目标商品及未来信息不能泄漏到 Memory、Planner
    Prompt、商品特征或检索索引构建流程；
-   模拟数据单独评测，不混入真实离线推荐指标；
-   保存数据快照、切分脚本、随机种子和数据版本。

Amazon Reviews
是评论/交互代理数据，报告中应准确描述任务为基于历史交互的下一商品预测或离线推荐评测，不应将其结果直接解释为真实购买转化率。

### 6.2 核心评测指标

  ------------------------------------------------------------------------------------
  模块                                指标
  ----------------------------------- ------------------------------------------------
  TIGER                               Recall@K、NDCG@K、MRR、生成合法率、解码成功率

  E5                                  Recall@K、NDCG@K、MRR

  Candidate Fusion                    Recall@K、NDCG@K、候选覆盖率、重复率

  Reranker                            NDCG@K、MRR、排序前后对比

  Judgment                            人工审核一致性、判断错误案例、结构化输出成功率

  Controller                          REPLAN/STOP
                                      决策质量、不必要重规划率、过早停止率、预算消耗

  Generator                           商品事实准确性、理由可追溯性、输出有效率

  Memory                              记忆检索命中情况、更新正确性、用户隔离测试

  End-to-End                          完整成功率、P50/P95 延迟、API 调用次数和成本
  ------------------------------------------------------------------------------------

### 6.3 必须完成的召回消融

至少比较：

1.  E5-only；
2.  TIGER-only；
3.  TIGER + E5；
4.  TIGER + E5 + RRF Fusion；
5.  TIGER + E5 + Fusion + Reranker。

确保所有方法使用相同的测试时间范围、候选商品目录和评价协议。

### 6.4 Agentic 模块消融

建议比较：

-   无 Memory 与有 Memory；
-   无 Judgment 与有 Judgment；
-   固定停止策略与 Adaptive Controller；
-   无 Replan 与有 Replan；
-   无反馈更新与有 Memory Update。

报告每项消融对推荐质量、延迟、API
成本和失败率的影响。不能只报告指标提升，也应报告新增模块的成本。

## 9. 风险与停止条件

以下情况必须暂停扩展训练并提交评审：

1.  外部代码 License 不允许当前复用方式；
2.  外部代码无法适配本项目商品向量或用户序列，且适配成本不明确；
3.  RQ-VAE 出现严重码本塌缩，且调整后仍无法改善；
4.  Semantic ID 无法稳定映射回商品；
5.  生成器输出大量非法或无法解码的 Semantic ID；
6.  时间切分数据存在用户行为或目标商品泄漏；
7.  训练资源超出可用预算；
8.  Phase 4 预计无法在项目期限内完成。

遇到上述问题时，应提交：

-   失败现象和复现命令；
-   日志、指标和资源数据；
-   影响的模块和验收项；
-   可行替代方案；
-   预计人时和资源成本；
-   对 Q12 完整验收的影响。

未经负责人批准，不得把 TIGER 双路召回改成 E5 单路并继续宣称 Phase 0--6
完整验收通过。

## 11. 最终执行原则

1.  **先 Pilot，后全量。** 不在没有 Pilot 证据时启动大规模训练。
2.  **先跑通 Agentic 链路，不等待 TIGER。** Phase 5 和 Phase 6
    可以先使用 E5 候选池开发和联调。
3.  **真实模型与 Mock 严格区分。** Mock
    只用于接口测试，不作为模型效果证据。
4.  **真实交互与模拟反馈严格区分。** 不将模拟反馈混入真实 TIGER
    序列或真实离线评测。
5.  **每个阶段有独立验收证据。**
    代码运行、模型有效和系统完整是不同层次的验收。
6.  **不擅自改变已确认决策。**
    资源或兼容性问题必须提交证据和替代方案，由负责人批准后修改。

**本项目 Phase 4
的最终目标是得到一条真实、可复现、能从用户历史生成商品候选的 TIGER
召回链路，并与 E5 形成双路召回；Phase 5--6 在此基础上形成可运行的
Agentic 推荐闭环；Phase 7 用严格的时间切分和消融实验验证系统价值。**
